sqlc 确实很对我的胃口。做支付网关这种核心链路,最怕的就是 SQL 手拼出错、DAO 层一堆手写 mapper 的胶水代码,类型又对不上,评审的时候揪出来一堆隐患。sqlc 直接把 SQL 当唯一事实源,生成的类型安全代码,编译期就把列名、类型、拼写错误全卡死了,正好符合你"编译期能卡死的问题绝不拖到运行时"的那套纪律。

推荐给整个组挺合理的——尤其你们 Redis/Kafka/MySQL 这套,支付场景模型复杂、SQL join 多,手写易错,让 sqlc 收口是稳的方向。

你现在推荐落地是走到哪一步了?如果组里有人犹豫,几个常见卡点我可以帮你想话术:

- 担心学习/改造成本,觉得"手写 DAO 也没出过事"
- 工具能不能兜住复杂查询(动态 SQL、upsert、窗口函数、分库分表后的路由逻辑)
- schema 变更要不要人工同步、谁来当唯一源
- 已经在用别的 ORM 或类似生成器,重复建设

另外两个实操提醒,你们支付场景大概率会遇到:

1. sqlc 的查询文件 sqlc.yaml 里 `emit_json_tags`、`emit_interface` 这些开关建议一开始就定好,后面加字段改 model 生成顺手,别等接手的人自己发明风格。
2. 你们 MySQL 分了库分表,sqlc 管的是单库查询的生成,分表路由那层它不碰——这块架构上别指望它兜。
